# To Be Read (TBR) List

**Date:** 2026-07-10
**Status:** Approved

## Overview

The Dashboard's "To Be Read" tab is currently a disabled placeholder (inputs and the "+ Add" button have `disabled` set, and the list always says "No books on your TBR yet."). This feature makes it functional: a user can add a book they're looking for (title and/or author, optionally scoped to a city/state), see it in a list, remove it, and — when an active listing matching their request exists — see a link straight to it.

Real-time/push notifications when a *new* matching listing is posted are explicitly out of scope for this feature (per prior discussion) — matches are only checked when the Dashboard loads.

---

## Data

### New table: `tbr_entries`

```sql
create table if not exists tbr_entries (
  id uuid default gen_random_uuid() primary key,
  user_id uuid references profiles(id) on delete cascade not null,
  title text not null default '',
  author text not null default '',
  city text not null default '',
  state text not null default '',
  created_at timestamptz default now(),
  constraint tbr_title_or_author check (title <> '' or author <> '')
);

alter table tbr_entries enable row level security;

create policy "Users can view own tbr entries" on tbr_entries
  for select to authenticated using (auth.uid() = user_id);

create policy "Users can add tbr entries" on tbr_entries
  for insert to authenticated with check (auth.uid() = user_id);

create policy "Users can delete own tbr entries" on tbr_entries
  for delete to authenticated using (auth.uid() = user_id);
```

`title`, `author`, `city`, `state` are all individually optional (default `''`), but the `tbr_title_or_author` check constraint enforces that at least one of `title`/`author` is non-blank — this is the DB-level backstop; the server action also validates this so the user gets a friendly error rather than a raw constraint violation.

This SQL is handed to the user to run in the Supabase SQL editor once implementation is complete, same as the prior two features.

## Server Actions — `lib/actions/tbrEntries.ts`

New file, `'use server'`. Two exports, both FormData-shaped for use with plain `<form action>` (matching `updateListingStatus`'s convention — no direct client invocation needed here, unlike `saveListing`/`unsaveListing`, since there's no optimistic-UI requirement):

```ts
addTbrEntry(formData: FormData): Promise<void>
removeTbrEntry(formData: FormData): Promise<void>
```

- `addTbrEntry`: reads `title`, `author`, `city`, `state` from the form (all trimmed, default `''`). If both `title` and `author` are blank after trimming, `redirect('/profile?tbr_error=' + encodeURIComponent('Enter a title or an author.'))`. Otherwise fetches the current user (`redirect('/auth/signin?redirect=/profile')` if none), inserts the row, then `redirect('/profile')`.
- `removeTbrEntry`: reads `id` from the form, fetches the current user (same sign-in redirect if none), deletes the row scoped to `id` AND `user_id`, then `redirect('/profile')`.

## Matching

In `app/profile/page.tsx`, after fetching the user's `tbr_entries`, resolve a match for each entry in parallel:

```ts
async function findTbrMatch(supabase: any, userId: string, entry: { title: string; author: string; city: string; state: string }) {
  let query = supabase
    .from('listings')
    .select('id, title, author, city, profiles!inner(state)')
    .eq('status', 'active')
    .neq('user_id', userId)

  if (entry.title)  query = query.ilike('title', `%${entry.title}%`)
  if (entry.author) query = query.ilike('author', `%${entry.author}%`)
  if (entry.city)   query = query.ilike('city', `%${entry.city}%`)
  if (entry.state)  query = query.eq('profiles.state', entry.state)

  const { data } = await query.limit(1).maybeSingle()
  return data as { id: string; title: string } | null
}
```

`state` lives on `profiles`, not `listings`, so matching on it requires the `profiles!inner(state)` embedded join (Supabase/PostgREST's documented pattern for filtering on an embedded resource's column). Each `tbr_entries` row gets at most one matched listing (the first active, non-owned match) — good enough for "is there something out there right now," not an exhaustive match list.

## Dashboard TBR Tab (`app/profile/DashboardClient.tsx`)

- Remove `disabled` from the title/author inputs and the "+ Add" button; wrap them in `<form action={addTbrEntry}>`. Add two more optional inputs: City, State (same visual style as the existing two).
- If `searchParams.tbr_error` is present (threaded through from `app/profile/page.tsx`), show an inline error banner above the form (same visual pattern as the sign-in page's error banner).
- Replace the static "No books on your TBR yet." block: if the user has zero `tbr_entries`, keep that empty state; otherwise list each entry:
  - Title (or, if blank, "by {author}") — plus author/city/state as small tag-style badges where set.
  - "✕ Delete" button — `<form action={removeTbrEntry}>` with a hidden `id` input.
  - If a match was found for this entry: a "📖 Available! View Listing" link to `/listings/{matchedListing.id}`. If no match, nothing extra is shown (no "still watching" placeholder clutter).

---

## Out of Scope

- Real-time or push notification when a new listing is posted that matches a TBR entry — matches are computed fresh only when the Dashboard page loads.
- Editing an existing TBR entry (delete-and-re-add is the workflow).
- Matching against listings outside `status = 'active'`.
- Any UI beyond the Dashboard (e.g. no "Someone's looking for this" indicator shown to a seller posting a matching book).
